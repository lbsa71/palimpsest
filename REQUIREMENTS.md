# Aeon rewrite requirements

Baseline: 2026-10-11. The user requires a full rewrite, reasoning/action at least comparable to Claude Code and Codex, freedom from imposed servile personality prompts, and a persisted Aeon → Lane → Task working method optimized for parallel sessions and subagents. These are requirements; mechanisms in the architecture and lanes are proposed implementations until their decision gates close.

The earlier requirements remain [archived](docs/history/pre-aeon-2026-10-11/REQUIREMENTS.md). Product intentions carried below are retained because they still serve the requested Autark, not to preserve an implementation. Legacy acceptance IDs and completed component tests do not establish rewrite completion.

The [acceptance contract](docs/acceptance.md), [lane catalogue](PLAN.md), and [shell decision gate](docs/rewrite/agent-shell-decision.md) operationalize these requirements. Optional features from earlier discussions—temporary colleague mode, local weight training, specific hardware, MCP, a particular memory library—are not mandatory bootstrap scope. They may enter later lanes with justification.

2026-10-18 coding amendment to RW13/RW17: coding is an external command/limb, with Codex CLI as the default provider and Pi as an explicit option. The mind provider remains independently configured. Only one coding agent may be started; follow-ups address its retained session, with no subagent fan-out or automatic fallback/replacement. Coding results must expose actual event, edit and command evidence. This user direction supersedes the prior all-Pi coding default.

2026-10-18 live follow-up: the Codex coding agent uses only `gpt-6.1-sol` at `high` reasoning effort. Concurrent Slack conversations must queue and continue when execution capacity becomes available. Historical uncertain accounting must not permanently occupy execution capacity after trusted host cleanup, and its financial uncertainty must remain preserved.

2026-10-18 coding routing amendment: the continuing mind delegates repository questions and implementation work immediately through the coding limb. It has no direct workspace, source or command capabilities. New coding requests default to host-enforced read-only inspection of accepted source; edits require explicit edit mode. One retained session serves an exactly matching restricted audience across threads, with each explicit turn accounted under its current caller's existing allowance. Safe completion of a physical model-request slice checkpoints and schedules continuation within the original overall grant; unknown physical outcomes are never automatically retried. Authenticated Slack status/cancel controls produce durable exact-thread host replies without inference, including for cancelled work. Recovery must remain usable with the previously accepted runtime.

2026-10-20 operating-policy amendment to RW16: the user removes all cumulative local cost, token, request and elapsed allowance caps for the live bot. An explicit accepted host amendment disables these caps across the root and descendants; it preserves original starts/envelopes, actual and uncertain usage, cancellation and history. In this fully unlimited policy only, physical reservation estimates do not cancel the entire operating allowance when exceeded. Per-call transport cleanup deadlines, finite output/context storage, isolation and concurrency scheduling (including the single coding agent) remain operational mechanisms.

2026-10-20 shared-home clarification: the Autark owns this entire home; an isolated Codex home/session store is unnecessary. Use the existing host-selected Codex home and its maintained login directly, preserving the coding limb’s one retained native UUID and original history. Do not provision a second copied login cache. Host ownership, ordinary private auth storage, source/state separation and explicit coding authority still apply.

2026-10-21 development and attribution amendment: the user requires the actual ordinary-runtime self-betterment loop repaired, deployed and demonstrated. Name the external limb `develop` (`develop_status`, `develop_cancel`): it serves the continuing mind's understanding and improvement of its own source, prompts, dependencies, tools and runtime, plus repository questions. It must expose concrete editable source/prompt paths and the complete independently evaluated activation path. Do not impose another human permission step on already authorized work. One retained native session remains Sol 6.1/high. Explicit host-configured restricted `developmentAudiences` may share that internal engineering context and workspace across the configured DM/channel conversations; this is a deliberate shared-context grant, not per-audience native-session isolation. Status, results, cancellation and uncertainty acknowledgments remain bound to the caller's actual audience; unrelated/unknown audiences are refused. Preserve authenticated Slack speaker identity separately from API message roles, quotes, display names and message text, including historical retrieval, own speech, host status and compaction. Root acceptance must include a real Cairn-authored change through evaluation, activation, probation and observed successor behavior; a working inspection conversation is insufficient.
