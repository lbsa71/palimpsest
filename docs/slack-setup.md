# Connect the local seed to Slack

Use Socket Mode so the local process connects outward to Slack without a public webhook URL. It is implemented and connected to `serve`; fixture tests, live bot authentication and a native Socket Mode connection have passed. A user-initiated mention also completed through Mistral and delivered a thread reply after fixing worker recovery with accumulated history. Signed HTTP ingress remains an alternative. Automatic joined-thread history recovery is implemented in the 2026-10-11 source change; its installation and live recovered-message delivery remain pending.

1. Open [Slack app management](https://api.slack.com/apps), choose **Create New App → From a manifest**, select the workspace, and paste [the manifest](../config/slack-app-manifest.json).
2. Install the app to the workspace. Copy the **Bot User OAuth Token** from **OAuth & Permissions** into `SLACK_BOT_TOKEN` in the private external credentials file `~/.config/palimpsest/credentials.env`.
3. Under **Basic Information → App-Level Tokens**, generate a token with **connections:write**. Put its `xapp-…` value in `SLACK_APP_TOKEN` in that same private file. Socket Mode is enabled by the manifest; no signing secret or public URL is needed for this transport.
4. Invite Palimpsest to a dedicated test channel. Fill in the workspace (`T…`), your member (`U…` or `W…`) and optional channel (`C…`) IDs in `SLACK_ALLOWED_TEAM_IDS`, `SLACK_SELF_MODIFICATION_USER_IDS`, and `SLACK_ALLOWED_CHANNEL_IDS`. A channel link typically contains workspace/channel IDs. Your profile menu provides **Copy member ID**. Each setting can contain comma-separated IDs. A workspace allowlist is required; the member list determines self-modification suggestion eligibility, while all human participants in configured scopes can converse. If the new member setting is absent, legacy `SLACK_ALLOWED_USER_IDS` is used; an explicitly blank new setting denies everyone modification eligibility. An omitted or blank channel setting adds no channel restriction, so a dedicated channel allowlist is recommended when limiting the test to one channel.
5. Keep the credentials file mode `0600`. Configure the intended model/provider before the first bootstrap, then run `npm start -- doctor` from a clean checkout. This reports credential presence and allowlists without making network calls; it does not validate tokens or live Slack access.
6. Stop any other coordinator for the same external state directory, then run `npm start -- serve`. With the bot and app token set, the startup record should contain `slackSocket.state: "connected"` and `slackUrl: null`. Initial connection failure exits the service; correct the configuration before retrying. The startup state confirms an opened socket, not successful message delivery.

The workspace ID can be obtained from [`auth.test`](https://docs.slack.dev/reference/methods/auth.test) using the saved bot token; in the browser Slack URL it is the `T…` segment after `/client/`. Open your own profile → **More → Copy member ID** for the human modification whitelist. The `user_id` returned by `auth.test` with a bot token identifies the bot, so do not use it as your member ID. App ID and Client Secret are not used by this Socket Mode setup.

The manifest requests `app_mentions:read`, `chat:write`, `channels:history` and `groups:history`, and subscribes to `app_mention`, `message.channels` and `message.groups`. Mention `@Palimpsest` to start or invite it into a thread. Subsequent messages and `status`, `cancel`, or `correct` controls in that joined thread need no mention. These are ordinary messages, not registered slash commands. Commands must target a task from the same thread; obtain its ID from local task/event records. Unrelated top-level messages, unjoined threads, bots/subtypes and DMs are ignored. All admitted human participants share that thread context. Cancellation/correction requires the original authenticated task author.

For an existing installation, update its **App Manifest** with the new subscriptions/scopes and save. Under **OAuth & Permissions**, **Reinstall to Workspace** and authorize the new channel history scopes. These permissions deliver channel events and allow the new joined-thread reconciler to read history; only admitted messages enter ordinary task storage. Verify that the saved bot token remains valid after reauthorization, and update the private credentials file if Slack issues a replacement. Restart the service to load the changed ingress rules. An existing thread with a durable Slack task is already joined; send a fresh unmentioned follow-up to test. Previously unjoined conversations are not discovered by recovery; retained joined-thread messages are scanned subject to the documented bootstrap floor.

Save tokens only in the external private file, never in this manifest, Git or chat. After the connection is verified, send an explicit mention in the test channel to request a reply. Setup and authentication checks do not themselves authorize unsolicited channel messages.

Normal Socket Mode refreshes reconnect automatically. Repeated failures back off, then cool down before retrying; a disabled Slack link stops automatic reconnection. See the [Socket Mode contract](slack-socket.md). The startup record is a snapshot. The new source exposes operator-authenticated `GET /slack/status` on the local API for current `socket` and `recovery` observations; peer credentials cannot read it. Check recovery errors/pending threads separately from socket connectivity.

For signed HTTP instead, omit `SLACK_APP_TOKEN`, supply `SLACK_SIGNING_SECRET`, disable Socket Mode in the Slack app, and configure its Events API Request URL through an operator-controlled HTTPS forwarder to the `slackUrl` printed by `serve`. That loopback URL uses a separate ephemeral port. The bundled manifest enables Socket Mode and does not configure a public Request URL. See the [runbook](runbook.md) for lifecycle, state and forwarding limits.

References: [Slack Socket Mode setup and protocol](https://docs.slack.dev/apis/events-api/using-socket-mode/), [app manifest reference](https://docs.slack.dev/reference/app-manifest/), [app mention event](https://docs.slack.dev/reference/events/app_mention/).

On 2026-10-08 the installed app was updated and reauthorized, both history scopes were confirmed on the saved bot token, and a fresh unmentioned follow-up succeeded in an existing mentioned thread with a delivered reply. Setup/restart fixture coverage and that historical live observation remain separate evidence. They do not establish delivery by the new recovery implementation.

The recovery integration is enabled by default whenever `serve` has Slack configured. It uses the existing bot token and history scopes; this installation's read-only `auth.test`/`conversations.replies` check passed without a new token or OAuth grant. No recovery-specific environment setting is required. It scans joined threads at startup, one minute after each pass, and after Socket Mode reconnection, with ten pages per pass and 100 requested items per page. See [communications](communications.md#automatic-joined-thread-recovery-2026-10-11) for durable checkpoints, two-second visibility lag, sixty-second overlap, rate-limit handling, legacy coverage floors and ordering limits. Offline first mentions/new threads remain outside coverage; already queued live work and Slack retention/visibility limits must not be confused with complete historical replay.
