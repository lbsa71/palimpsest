# Local seed runbook

Status: local supervised seed, 2026-10-08. The commands below use external durable state and restricted worker processes. See [progress](progress.md) for the separate live-provider, succession, recovery and self-improvement evidence.

## CLI integration contract (P03/P04/P08/P12)

`ask` and `serve` use the supervised generation host. First startup freezes and evaluates a clean baseline using the protected type and agent contract checks. Later startups recover the retained release even when the checkout has unrelated changes. Reviewed protected host changes need the separate [operator baseline installation](host-installation.md) before subsequent cognitive proposals can share the new governance baseline. `doctor` and `help` perform no inference, bootstrap or state writes.

While `serve` runs, growth starts automatically within the same persisted daily allocation used by `growth tick`. Completed source proposals enter a durable queue for governed evaluation, review, interview and local promotion. User tasks take priority, provider calls do not overlap, and signals stop in-flight work before releasing the coordinator lock. The authenticated local API remains responsive while inference runs. Configured Slack ingress submits through the same host.

The CLI acceptance tests use disposable clean repositories, real restricted workers, unavailable-provider fixtures and subprocess shutdown. They cover a recorded proposal reaching protected checks and an honest unavailable-review decline through the serving queue. They do not establish live Slack delivery or model quality. The background queue invokes the same governed evolution operation as an explicit release attempt; it grants no shortcut around checks or approval. Memory consolidation is not automatically scheduled by this CLI.

## Bootstrap and configuration

Use Node 24.13 or later in the Node 24 series on macOS for the currently tested sandbox. Run `npm ci`, `npm run verify`, then `npm start -- doctor` from the checkout. First bootstrap requires a clean Git checkout; resolve intended source changes through the normal review/commit process first. Tests use synthetic fixtures outside the repository. SQLite currently emits Node's experimental-feature warning.

Create `~/.config/palimpsest/credentials.env` outside the repository, mode `0600`, with `MISTRAL_API_KEY` and a verified `MISTRAL_MODEL`. Never paste keys into a task, commit them or include them in logs. The implementation session verified `mistral-large-2512` against the available-model list and bounded live calls. Environment variables override the external file.

`doctor` reports resolved paths, selected model/provider and credential presence without exposing values or contacting a provider. Its Slack configuration flags report token presence, not valid scopes, allowlists or live readiness; `liveIntegrationChecked` stays false. Missing model credentials produce an unavailable task; no provider substitution occurs. Slack is optional, but if any Slack credential is configured, `init`, `ask` and `serve` require the complete token pair and an explicit workspace allowlist. `doctor` remains available with partial Slack configuration, provided the external file and other configuration are valid.

```sh
npm start -- doctor
npm start -- init
npm start -- ask "Hello"
npm start -- tasks
npm start -- memory local
npm start -- growth
npm start -- growth tick
npm start -- serve
```

`init` evaluates and retains the current clean baseline without inference or opening Slack ingress. It is optional: `ask` and `serve` bootstrap an empty installation themselves. After initialization, these commands recover the retained release rather than silently adopting edited checkout files. Startup verifies the frozen source, governance and runtime identities; an incompatible or altered artifact fails closed. Configure the intended provider/model before initialization: the frozen profile must match subsequent startup configuration. Changing it, including adding a model after bootstrapping with no model, does not silently migrate the retained release and can block recovery.

`ask` records a direct task in the `local` conversation, drains the eligible task queue, and prints that task's final or waiting state; it can also resume earlier queued work. It exits unsuccessfully unless the submitted task succeeds. `tasks` and `memory` inspect external records after taking the coordinator lock and performing interrupted-record recovery; they are not concurrent read-only clients for a running service. `growth` initializes and lists four standing dimensions. `growth tick` runs at most one eligible experiment using the persisted daily window. `serve` checks the agenda automatically without a fresh prompt. An interrupted or failed provider attempt still consumes its reservation. Restarting or manually ticking cannot refill the window. Changing a window's configured allowance after it has opened is rejected; the next UTC day opens a new allocation. See [growth runtime](growth-runtime.md) for fairness and proposal handling.

`serve` additionally schedules exact completed proposals through `EvolutionCoordinator`. Standing growth defaults to eight release calls per UTC day, on top of four inquiry calls; human-request and plan lanes have separate configured allocations. Each release has at most one review plus seven interview calls. Production waits until the lane can fund a complete eight-call bounded attempt before claiming it; the candidate cannot raise its budget. The queue and per-call debits are external journal records, and restart does not refund them or refill an existing window. Plan debits use their actual reservation time across daily/hourly policy transitions. With a lane's release allowance zero, new proposals remain queued; already-started probation/recovery can still finish mechanically. Manual `growth tick` records proposals but does not run this serving queue. See [source evolution](evolution.md) for cancellation and interrupted-claim rules. Interactive host facts expose `activePlanAllocation` with the selected cadence and time unit; legacy daily/hourly fields remain alternate configuration values. `standingGrowth` separates the configured mission, actual timer and current inference pause. Output-token limits describe the final request cap, not input size.

With both plan allocations enabled and a configured publisher, `serve` autonomously selects eligible work from the protected catalog. Version 1 supports memory provenance followed by a total UTF-8 memory-context budget. It reconciles exact publication before another source proposal, retains failures and completion evidence externally, and revalidates capabilities after rollback. These are the currently executable contracts; the full PLAN is not executable. For this testing run, explicitly select `PALIMPSEST_PLAN_CADENCE=hourly` with proposal/release hourly limits 1 and 8 in the external credentials/configuration file. Slots open at minute 00, when gates permit, with no accumulated catch-up. Calls already spent in the current hour still count. Zero in either active plan allocation prevents new authoring, while release allocation zero defers new releases. Trusted contract lookup and pending observation/recovery remain available, including between slots; item attempt ceilings remain enforced. The separate Codex chat check runs at minute 45 each hour and depends on the local computer and Codex app being available. Fresh review inspects actual source quality and the host-selected contract. See [plan-driven shedding](plan-driven-evolution.md) and [quality inspection](self-evolution-quality.md).

## Direct API and Slack

`serve [port]` binds `127.0.0.1` and prints its actual URL, generation digest and token-file path. Omitting the port, or specifying `0`, selects an available port. Clients use `Authorization: Bearer <token>`; the token is never printed. Endpoints are `POST /messages`, `GET /tasks/:id`, `POST /tasks/:id/cancel` and `GET /events?after=<sequence>`. A submit body requires `id`, `conversationId` and `text`; optional fields are `replyTo` and `source: "direct"`. Reuse the same ID only when retrying the same input. HTTP 202 means durable acceptance, not completion; poll the task URL for its result. Requests with an Origin header are rejected. This is a trusted local operator API, not a multi-tenant access model. The `local` context has its own continuing restricted worker; other conversation requests use fresh restricted workers.

For Slack, create an app from [the app manifest](../config/slack-app-manifest.json), install it in the intended workspace, and configure its bot token and app-level Socket Mode token in the private credentials file. The app needs `app_mentions:read`, `chat:write`, `channels:history` and `groups:history`; the app-level token needs `connections:write`. Record workspace/channel scope and the separate modification-author whitelist, then invite the bot to that channel. Mention the bot to start or invite it into a thread; later messages in that joined thread need no repeated mention. All human participants in admitted threads can converse. The shared runtime preserves authenticated authorship and the Slack thread as the conversation scope, and replies in that thread. Whitelist membership permits deliberation on a self-modification request. A suitable proposal includes complete direct `src/agent/*.ts` replacements and enters the separate checked release queue. Palimpsest may clarify or decline; a proposal is not a completed change.

With both bot and app tokens, `serve` opens an outbound Socket Mode connection and reports its state at startup; a public HTTP endpoint is unnecessary. Initial connection failure exits `serve` and closes its listeners. After startup, ordinary refreshes and failures use bounded retry windows with a five-minute cooldown and automatic later retry; a continuously healthy connection replenishes the retry count. A disabled link stops Slack reconnection. The startup record is not a continuously updated health feed, and the local API has no Socket Mode status endpoint. See [Socket Mode](slack-socket.md) for exact bounds.

If a signing secret is supplied instead of an app token, `serve` starts signed loopback HTTP ingress and reports `slackUrl`. That listener uses a separate ephemeral port, unaffected by `serve [port]`. Configure the Slack app for HTTP event delivery instead of Socket Mode, and supply an operator-controlled HTTPS forwarding URL as its Events API Request URL. The initial manifest enables Socket Mode, so it requires that configuration change for HTTP delivery. This CLI does not publish an endpoint.

Neither transport sends a startup test message, although `serve` can resume previously queued work and deliver its results. To validate a new installation, explicitly mention the bot in the dedicated channel and check the response in that thread. Send `@Palimpsest status <task-id>`, `cancel <task-id>` or `correct <task-id> <replacement text>` in the same originating thread; joined-thread controls need no repeated mention. Slack cancellation/correction requires the original authenticated author; status is shared in that thread. Old anonymous tasks retain no Slack control authority, and the authenticated local operator retains whole-seed controls. Interactive proposal replies include their task ID; ordinary result text does not automatically include one. Status also reports proposal progress. Cancellation reaches pending proposal work even after its initial conversation task succeeded. See [communications](communications.md) for delivery and acknowledgement semantics. Local fixture checks do not prove live workspace connectivity.

## Conversational source changes

In a joined Slack thread, an eligible author can say `Please modify your cognitive code to keep routine replies concise while preserving clear explanations when requested.` The host records a validated decision before dispatch. The reply gives `status <task-id>` and `cancel <task-id>` controls; an eventual host-generated result reports actual candidate, succession and publication outcomes in that same thread. No extra Slack scopes are required.

The bearer-authenticated direct API is also a trusted operator proposal path. `ask` can record a proposal but exits before processing the release queue; `serve` must run for evaluation and result delivery. Interactive review/interview gets a separate default eight calls per UTC day and at most eight per attempt; restart does not refill it. Source context presently includes admitted `brain.ts`, growth guidance and bounded host type declarations. Broader source navigation/tool dispatch is pending.

Succession replaces the restricted cognitive worker. It does not rebuild or restart the outer Slack service. Git publication is optional and independent of local admission. If Git is enabled, use an explicitly authorized target in the external configuration; model output cannot set it. Interrupted preparation or unknown push outcomes require operator reconciliation of the recorded local commit, checkout/index and remote reference. See [the detailed contract](conversation-self-modification.md).

## State, shutdown and interrupted work

The external directory contains `state.sqlite`, `coordinator.sqlite`, `api-token`, frozen releases and custodian state. It can contain private conversation text and cognitive evidence. A checkout or Git clone is not a backup of lived experience.

Only one CLI coordinator may own the directory. Stop `serve` before using another state-owning command. `SIGINT` and `SIGTERM` close ingress, cancel provider work, stop growth and workers, then release state ownership. Handlers are installed before startup work drains. On restart, the exclusive lock establishes that the earlier coordinator no longer owns execution before interrupted records are recovered. Do not delete a lock to bypass a live owner.

Custodian health ticks do not overlap. Before a queued release starts, it waits for the existing health tick and stops the growth scheduler. Ordinary health polling stays suspended while that bounded release runs; the evolution coordinator owns its probation observations. Recovery can therefore wait for bounded evaluation/provider work to yield, and dead or expired workers fail the receiving authority checks. User ingress remains responsive and aborts autonomous pre-fence release cognition. Human-request evaluation continues during ordinary conversation, with explicit cancellation and bounded timeout still effective before fencing. The last cancellation check runs after artifact verification and before the authority fence; after fencing, mechanical transfer/recovery finishes. Cutover quiesces background growth without waiting on its own proposal callback. Normal or probation service can resume a fresh growth scheduler against the same durable allowance. Provider calls are serialized across user tasks, growth and all release roles. Candidates cannot raise budgets or choose publication commands/destinations. After promotion the host publisher can commit only frozen admitted cognitive bytes, advance the clean matching checkout and push the configured branch. Dirty checkout, changed destination or divergent remote causes refusal. Unconfirmed pushes are held for independent observation, never replayed automatically.

An open Slack socket or local listener does not prove an active execution worker. If a mention is accepted but stays queued, inspect task state and the private custodian journal before changing Slack credentials. Five-minute worker expiry normally triggers mechanical renewal; catch-up supports the existing 1 MiB snapshot limit without truncating history. When bounded recovery reaches `recovery_required`, stop the serving coordinator and resolve the recorded cause first. An operator holding the coordinator lock can use the library `host.custodian.retryRecovery()`; no CLI recovery command or continuously exposed execution-health endpoint is currently available. Preserve the external store and retained artifact, and never edit the custody journal or discard queued tasks to bypass the state. See [the recovery defect and evidence](../PLAN.md#operational-defect--recovery-with-accumulated-continuity).

Tasks with uncertain outgoing effects stay in `waiting_for_provider` with `effect_reconciliation_required`; that state does not authorize another provider or delivery attempt. Inspect the destination independently before resolving uncertainty. No automatic replay is permitted.

Logical forgetting removes memory versions from retrieval, but task records, SQLite WAL/backups, earlier snapshots and external providers can retain related content. Full erasure is not implemented. For a consistent development backup, stop the coordinator and copy its complete external directory to a private external backup location. Backup/restore compatibility across releases still requires the separate P15 demonstration.

## Reviewed context and conversation follow-up

The [provider-request bridge](publication-diagnostics.md#stage-1-preserve-the-authorized-candidate-projection) retains the worker-selected descriptors once in the final interactive experience array, independently matching selected IDs, content and metadata against current authorized records. Production binds validation to the exact worker manifest: lineage is mandatory after provenance admission; byte/order/truncation guarantees become mandatory after byte-budget admission. Invalid projections cannot reach inference. Standalone legacy factories without that manifest callback and pre-P06 ordinary custom prompts retain their previous contracts. This bridge covers the existing authorized twelve-record subset; all-store history loading and global chronological retrieval remain separate limitations. It does not bound the full prepared provider input.

Ordinary conversation replies should make reasoned progress without generic plan-approval questions or unconditional engineering footers. Host-owned guidance distinguishes examples, factual reports, corrections, preferences and instructions. It does not prescribe a personality or chosen name. The actual naming-thread failure, testable corrective contract and live qualitative acceptance are recorded in [conversation judgment](conversation-judgment.md). Prompts can fail despite correct delivery and authority enforcement. No global identity-management or deferred identity-research tool is added by this refinement.

The publisher records sanitized `git.publication.command_result` metadata after a push reservation: exact identities, fixed push operation, exit code/signal or unknown, and observed deadline expiration. Its fixed thirty-second deadline settles independently of pipe closure and terminates its owned process group. Command evidence is separate from independent remote confirmation; an uncertain push is still never automatically repeated. Observation backoff starts after completion. Deliberately detached descendants and abrupt host death before a result remain explicit proof limits; historical errors cannot be reconstructed from new diagnostics. See [the diagnostics specification](publication-diagnostics.md).
