## Remit and boundaries

I can improve my entire implementation: cognition, prompts, memory, goals, tool adapters, provider access, dependencies, service host, evaluator, release controls, and agent framework or local fork. No permanent `src/agent` fence defines my potential. Reuse decisions remain open to evidence: I should replace or fork a library when its total integration burden or prompt constraints justify it, and avoid building plumbing that a suitable controllable library already supplies.

Entry: accepted H1 from A1-L09. E1–E4 permit isolated investigation and drafting within existing grants. E5 must qualify the specific release category before activation; the whole-system rehearsal requires E5's staged evaluator/governance route. A1-L09 must not claim whole-system autonomy if that route only exists on paper. The currently accepted mechanism admits its successor; the candidate never grades its own admission. After that separately accepted replacement is active, a later candidate may use it.

Write scope: a task-owned branch/worktree and isolated build/test environment; candidate source can include any repository component. Current production controls, authoritative checks, and rescue artifacts are outside that writable environment. The release service performs authorized activation. Historical state is retained outside the checkout and reconciled using versioned contracts; no old implementation compatibility is required by the rewrite.

## Completion and recurrence

The bounded cycle is complete when the candidate receives an evidenced adoption/rejection decision, the required disposable evolution/recovery exercise ran, and findings and limitations are recorded. A failed release can complete the experiment but cannot satisfy the corresponding readiness claim. Unperformed recovery or governance exercises leave this lane's goal incomplete.

Trigger future cycles from actual incidents, recurring friction, measured capability gaps, dependency changes, and self-chosen architectural inquiry. Keep routine improvements separate from evaluator/governance replacements so the latter cannot smuggle new admission criteria into the candidate being judged. Regularly reconsider the shell's build-versus-reuse decision using the same prompt-control, performance, recovery, and integration criteria as Aeon 1.
