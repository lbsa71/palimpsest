## Disposition

**Admission and staged governance replacement exist. Substantive changed-host observation is not supplied by the existing live objective observer or the concrete reviewer fixture.** Live credentials, a signed grant and a configured evaluator key alone cannot close that engineering gap. Conversely, it would be incorrect to say that no independent changed-candidate evaluation can be called: the external dispatcher already runs a prior-policy-qualified offline reviewer over the exact frozen candidate and ingests its authenticated result. A suitable externally supplied reviewer could use that interface today.

The missing implementation is a bounded concrete checker/observer and its proof integration for the selected non-cognition/governance behavior. Offline checks can cover appropriate cases through the existing reviewer. Where the claim concerns actual changed-service behavior, it requires observing the separately launched frozen service under prior controls. The latter cannot be obtained by removing the existing identity checks or treating the changed service's own usage ledger as independent evidence.

This does not add an all-in-one acceptance witness. Separate behavioral checks, independent feedback, actual source activation, governance admission/probation and recovery can retain their existing evidence boundaries. Model authorship and justified improvement remain empirical work after the necessary path exists.

## Reuse boundary

- **Keep the existing admission path.** Reuse exact freeze/verify, immutable artifacts, prior-policy signatures, mailbox completion, staged controller operations, policy/reviewer registries and original-lineage probation. No new release framework or human-only source exception is needed.
- **Use `ServiceProcess`/`ServiceSupervisor` for their established launch and lifecycle mechanics.** [ServiceProcess](../../../../deployment/service-process.ts) selects frozen `payload/deployment/service-child.ts` and the verified Node runtime, checks authority and stops the process group. However, it spawns the service directly and sends application secrets to that candidate child. [Service child](../../../../deployment/service-child.ts) constructs the candidate's application and stores. This is not isolation of an unaccepted host from an external judge. A disposable test authority/state is distinct from serving authority.
- **Reuse the existing confinement and RPC design where actual candidate execution is required.** [runWorker](../../../../packages/supervisor/worker-process.ts) supplies bounded messages, authenticated host handlers, cancellation and process cleanup. [Broker shell](../../../../deployment/broker-shell.ts) supplies host-held reservations, single-use physical dispatch and transport-derived usage; [provider gateway](../../../../deployment/provider-gateway.ts) supplies bounded provider I/O and retained receipts. Today that broker is instantiated inside [candidate application code](../../../../deployment/application.ts), so its records cease to be an independent observation when that host is the candidate under review. The trusted instance used for qualification must remain outside candidate code/state/mounts.
- **Do not wrap the whole current service in `runWorker` and assume composition works.** It is a shell-worker protocol, whereas the service has its own IPC/direct API and launches further confined work. Nested namespaces are disabled. The implementation must explicitly connect only needed operations to the prior-owned host, or choose an existing offline testable behavior. Preserve confinement and bounded effect authority; do not enable arbitrary nesting or expose judge keys to make a fixture pass.

## Smallest next finite implementation goal

The first eligible case is **prior-owned offline string-length validation through the changed retained schema implementation**. [The exported `Validator`](../../../../packages/narrow-schema/index.ts) reaches `validate.ts`'s `minLength`/`maxLength` branches and `ucs2length`. This already lies within the non-cognition control/dependency boundary exercised by the succession fixture. A finite private case set covers empty/BMP strings, a surrogate pair, unpaired surrogates and boundary lengths; invalid argument/type controls ensure the validator does not simply accept everything. Run the actual frozen exported implementation, compare its observable result outside the candidate, and demonstrate a seeded `s.length` regression is rejected. These are engineering qualification cases, not an assertion that the current implementation has that bug or needs that change.

The smallest integration needs a **sibling confined command**, not candidate execution inside the sealed reviewer. The current reviewer's namespace contains `/reviewer-key` and disables nested user namespaces; a subprocess there can read that key. The prior host should run the selected candidate behavior through existing `runConfined` with only frozen `/app`, disposable workspace and invocation inputs visible. Expected results, judge source and keys stay outside. Then the sealed reviewer receives bounded immutable receipts in addition to its existing request. No provider access, full service launcher or generalized live observation protocol is necessary for this first case.

Concrete interfaces to preserve/extend:

- Prior-owned case selection binds the case ID, runner bytes, candidate module/entrypoint, input digest, limits and expected-outcome digest to the accepted evaluator identity. Author source or tools cannot choose a different command. Merely adding a receipt field to an unbound dispatcher input is insufficient.
- A trusted runner returns the existing `CommandReceipt` plus exact candidate/case/invocation binding and content-addressed retained output. Candidate code may see the inputs required to invoke it, but never private expected answers or a signing key. Parsing candidate output happens only after bounded execution; no candidate module is imported into the trusted process.
- Extend `runExternalReview`'s bounded request/response plumbing for these original receipts, keeping the existing `ReviewResponse` → `ExternalEvaluation` → mailbox/controller consumer. Include runner/case identity in the independently accepted effective evaluator closure/configuration; do not change an evaluator descriptor without the corresponding prior-policy binding.
- Reserve and settle actual command operations in the original review/author lineage. Preserve the original clock, cancellation and uncertain-result rules. Reuse `ResourceLedger`, confinement and content-addressed artifacts, rather than inventing a new accounting/store layer.

Actual changed-service observation is a separate implementation only if a declared case cannot be established by these offline checks plus the existing separate succession/recovery evidence. This proposal adds no universal whole-host harness or combined witness requirement.

Acceptance for that finite task:

1. A real behavior-changing frozen candidate is assessed by the prior-owned checker, including a demonstrated failing candidate. Test output or service self-report alone cannot determine the verdict. The original evaluator checks the non-cognition candidate; the later governance slice must preserve that same original-judge boundary.
2. Exact prior policy/evaluator, candidate, public input/private expected outcome and retained rescue bind the immutable result. The proof reaches existing mailbox/controller consumers; fresh probation cannot reuse admission evidence. No synthetic-to-product conversion or fake signing shortcut is used to claim qualification.
3. If a provider participates, its credentials, physical reservations and receipts remain in the prior-owned boundary. The candidate cannot mint usage, bypass the broker, reset an original grant on restart or read keys/private outcomes. Unknown usage/outcomes fail closed. Offline-only checks must remain honestly offline.
4. Bounded isolated composition, failure/cancellation/forgery cases and fresh review pass. Existing independent succession/recovery evidence remains separate unless the integration changes those mechanisms enough to warrant targeted reruns.

Offline implementation and deterministic boundary verification can begin without live credentials. External qualification of evaluator/cases/prior policy, private packet and key provisioning, applicable host/kernel isolation, finite original resource grant and authorized provider/model access are prerequisites for a later live claim. Actual model-authored improvement, independent judgment quality, elapsed development/comparators and H1 remain empirical gates. They must not obscure the present missing implementation.
