## Behavior to implement

The ordinary candidate's existing `ResourceLedger` and original `operating-envelope:v1` remain authoritative. Isolated control applications may retain their own operational stores and local budget bookkeeping. Those local rows never authorize physical dispatch independently of the original root. Reviewer sessions use an accepted role allocation under that same root. All roles retain separately fixed sublimits, configurations, closures, profiles and allowed effects; no role or restart creates a new spendable aggregate grant or resets the original issued-at/deadline.

Reuse the current ledger, synchronous host stores, durable runtime and Pi broker. A wrapper around `performRequest` alone is insufficient: it misses prompt capture, reservations, dispatch identity, retries, compaction and physical tools/effects. Intercept at a host-owned ledger/runtime composition boundary that covers both model and effect requests. Any application option is a trusted construction-time adapter, absent from candidate-controlled configuration and tools; the normal path remains unchanged. The author must freeze its concrete interface and fault ordering before implementation and coordinate shared application changes with root. Do not replace the existing resource implementation or introduce a distributed transaction framework.

1. Bind an externally accepted registration and exact role to the original ledger/store identity and an already accepted role allocation. Validate the original grant, root/start/deadline, role/profile/configuration/closure and any existing mirror mapping before dispatch. Use a deterministic role-scoped mapping for local run and physical request identities, including parent/reservation references; retain the original-to-local mapping. Candidate, controls and reviewer rows must not collide or count the same physical request twice.
2. Preserve complete allocation lineage and local sublimits. An isolated application can use its usual local root/run names, but every corresponding outer allocation descends from the registered role under the original root. Reopening with different configuration, profile, sublimit or mapping fails. An isolated store replacement cannot reset the outer role's lifetime or consumed resources. Local cancellation cannot cancel another role; cancellation/expiry of the original root blocks every descendant before physical dispatch.
3. Capture exact prompt manifest/payload or effect payload before original reservation. Pin request/provider/model/purpose/profile to the assigned role, with explicit allowed effect receivers separate from model profiles. The original durable reservation must exist before a control's local bookkeeping can lead to physical dispatch. Before entering any transport or receiver, the original request must be durably dispatched. A retry is a new physical identity and consumes a new reservation; compaction and reviewer evidence reads/checks are accounted work.
4. Record every original state transition in order, including reservation, dispatch, trusted settlement, cancellation and recovery uncertainty, with actual host observation time, immutable request identity, conservative ceiling/charge, raw payload/prompt/response references and the role/configuration/closure binding. Export types must match the frozen envelope's `DevelopmentRequestState`, `DevelopmentAccountingTransition` and transport attestation. The recorder, not a candidate/tool callback, retains raw bytes and signs transport facts. No candidate-reported token/cost values can release an outer charge.
5. Local and original stores are separate durable boundaries. Freeze and test each write/dispatch ordering explicitly. A crash after original reservation but before a local commit leaves that original reservation consumed; after possible dispatch it retains uncertainty/full charges until trusted reconciliation. Reopening must not dispatch a previously consumed physical ID again, erase an orphan or infer non-dispatch from a missing local row. Conservative refusal is valid where the existing evidence cannot establish a safe continuation. Such refusal must be reported as unavailable, not claimed as transparent recovery. Do not invent a cross-store atomicity guarantee.
6. Recovery of one control/reviewer must not mark another active role uncertain or restore/release its requests. The existing runtime's global `recoverDispatched` and authorized-effect recovery require careful scoping in the adapter. Existing candidate recovery semantics stay intact. Settlement and authentic later reconciliation may finish after cancellation, but cannot authorize additional work. Changes to shared ledger recovery semantics require a separate causal finding and root coordination.
7. Preserve the current physical ledger's charge semantics exactly: null usage holds ceilings; elapsed accounting conserves actual original lifetime and cumulative physical charges; overrun cancels the appropriate original allowance. The acquisition envelope's complete transition history can then verify observed concurrency and conservation. A final-state inventory alone is insufficient.
8. Before any model/receiver call, the finite acquisition recorder must reserve enough evidence capacity for request, response, settlement and failure records within the attempt's unchanged bounds. This bridge exposes the necessary pre-dispatch and post-response hooks to that recorder; it does not create a separate evidence allowance. Evidence exhaustion blocks dispatch or retains an honestly uncertain interrupted outcome. Generic release review and unrelated ordinary application use remain unchanged.
