Direct `runScreenCase`/lifecycle invocations cannot register a live grant; only the concrete host route owns those object bindings. The host constructs the fixed ordinary Mistral gateway. Process-based cases receive explicit secrets through inherited private IPC, without argv/environment/public boot/evidence copies. S12 uses exactly the accepted prior judging policy and actually loads the admitted current artifact.

The original root ledger begins at each signed Experiment's issuedAt. Ordinary tools, model/child/compaction requests, restart uncertainty, local reconciliation and private executable checks share those original clocks/allocations. Production resource machinery performs an actual kernel preflight only when the separately authorized host execution API is invoked. Authentication and preparation alone cannot establish kernel enforcement or independent competence.

Per-Experiment logical evidence includes original raw artifact/document/event contents, authority/local-receiver records, attempt/acquisition files, claim copies and report chunks/manifest. Duplicate retained contents count again; SQLite page/WAL allocation overhead and accepted deployment payload storage are separate infrastructure. Original8MiB/1,000,000-byte ceilings remain unchanged. Required overflow causes acquisition failure; its raw state is quarantined diagnosis rather than a successful bounded report. A failure receipt is reserved before dispatch. The signed outer metadata fields are named `maxPlanRecordBytes`/`maxPlanArtifactBytes`, without imposing an invented combined8MiB twelve-case budget. Private store bytes and entry slots are provisioned before signing and cannot grow/recreate a grant.

The source-level route will execute all predeclared attempts sequentially and retain case failures/late refusal; it cannot reset/retry until success. Initial simultaneous issue is explicit. Each Experiment remains bounded by its original fifteen-minute maximum. A longer outer plan does not extend any Experiment. Staged future activation windows would require a separately reviewed authenticated extension; no scheduler framework exists here.
