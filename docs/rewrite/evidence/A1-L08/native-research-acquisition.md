## Documentation facts, with limits

OpenAI's [Responses web-search guide](https://developers.openai.com/api/docs/guides/tools-web-search) describes a hosted `web_search` tool, search/open/find action records, citations and optional source lists. Search actions have tool costs in addition to relevant token costs. The [request reference](https://developers.openai.com/api/reference/cli/resources/responses/methods/create) documents a total built-in `max_tool_calls` bound. However, its [deployment checklist](https://developers.openai.com/api/docs/guides/deployment-checklist#use-multi-agent-for-parallel-work) says that bound is unsupported in the API's Multi-agent mode. These current API descriptions do not establish the exact emitted schema, supported controls or mode of pinned Codex 0.162.1. A wrapper must not assume a bound applies merely because its name exists in another API mode.

Claude Code's [tools reference](https://code.claude.com/docs/en/tools-reference#webfetch-tool-behavior) describes WebFetch as page retrieval followed, for most fetches, by a separate model extraction call. WebSearch may perform up to eight backend searches per tool call; it does not itself fetch result pages. The page also documents caching, retries and provider-dependent availability. Thus one visible native tool call is not a trustworthy count of physical requests, searches or model charges. Its current documented behavior is an acquisition lead, not proof about our installed profile.

The [Claude API web-search guide](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool) describes a distinct server-tool definition, a per-request `max_uses`, server result/citation blocks, encrypted continuation material and a separate search usage counter. Retain such bytes unchanged if actually acquired. Do not equate the API tool schema with the native CLI's WebSearch implementation without tracing it. Documentation pricing is neither a spending grant nor evidence that our account supports the path.

## Alternatives and decision

| Route | Benefit | Cost / limitation | Disposition |
|---|---|---|---|
| Keep each product's native research tools and add narrow observed protocol/accounting support | Best preserves the actual comparator's tool behavior and instructions; reuses its existing shell | Must observe internal searches, extraction calls, retries, sources and enforceable original ceilings; exact pinned surfaces remain unknown | First choice for acquisition; no hosted tool is enabled for paid transport by this document |
| Expose the existing host retrieval service through each product's supported tool integration | Reuses our tested HTTPS boundary and can provide the same source corpus to every shell | Requires a small acquired integration; changes the comparator's affordances and cannot be called its native best-system research result | Possible separately labelled same-affordance experiment if native integration is unsuitable; do not build a new general framework now |
| Enable broad direct network access or add an external agent platform | May expose more native operations quickly | Does not solve observed accounting/source attribution; broadens the system and instruction/configuration paths without demonstrated need | Not selected for this unit |

This is a comparator preparation decision, not a change to ADR 0032's source-owned Pi selection. No evidence here identifies a cognition failure in Pi or justifies replacing the Autark shell. If the native route proves unworkable, record the exact incompatibility and reassess the narrow alternative; do not turn missing access into a negative competence score.
