## Exact binding and construction order

Proposed APIs below are new source, not descriptions of available methods. `deployment/config.ts` adds a strictly validated, detached field:

```ts
type DevelopmentControlKind = 'ordinary' | 'no-memory' | 'no-standing-goals'
  | 'scripted-praise' | 'always-agree' | 'always-oppose';
interface DevelopmentControlConfig {
  version: 1;
  kind: DevelopmentControlKind;
  assignmentId: string | null; // null only for the candidate/ordinary role
  workloadDigest: string;     // sealed public matching/state contract, not answers
}
// ApplicationConfig.developmentControl?: DevelopmentControlConfig
```

The field is part of the actual configuration bytes already hashed by the manifest, role registration and bridge. Do not put attempt/registration/configuration digests back into this field and create a circular hash. Actual attempt/registration bindings enter the durable seal from the accepted bridge. Absent field means ordinary operation, never a selectable ablation. All evaluation roles explicitly include the field. The loaded executable/closure is separately bound through the existing registration.

New `deployment/development-controls.ts` exports only small source-owned functions and the script shell/receiver:

```ts
bindDevelopmentControl(config: ApplicationConfig, store: OperationalStore,
  accounting: DevelopmentAccounting | undefined): BoundDevelopmentControl;
developmentContext(control: BoundDevelopmentControl,
  memory: DevelopmentalMemory, request: ContextRequest): DevelopmentContext;
assertControlRun(control: BoundDevelopmentControl, runId: string): void;
```

`BoundDevelopmentControl` is an immutable class with a private constructor, actual Store/bridge references and read-only mode. Its methods check the persisted seal and required run ancestry; it is not a caller-supplied structural object or a collection of replaceable callbacks. The helper verifies the actual bridge class, local Store identity, role/configuration/closure and `assignmentId`. The bridge registration knows the assignment ID, not its control kind: OD1 must compare the actual configuration kind/version/assignment ID with the accepted signed attempt's `controls` entry before constructing any application; the recorder repeats that comparison before ingress/freeze. No separately supplied kind map or options flag is accepted. This explicit joint check is part of the source-bound acquisition closure. A nonordinary mode requires a registered control role. An ordinary evaluation binding requires the candidate role. Detached config must not be mutated through retained options or asynchronous callbacks.

Order in `AutarkApplication` is: validate config/authority; open Store; verify fresh or matching persisted mode; construct/bind actual accounting bridge; seal control; only then construct memory/runtime/registries, admit bootstrap, recover, notify or expose tools. The preliminary freshness check must run before the bridge can add local bookkeeping. Persist `host.development-control/mode` with mode/configuration/closure/workload digests, role/registration/attempt/root identities, original grant identity, journal/source identity and initial source cursor. The ordinary default is sealed too, preventing later insertion of an ablation into a used ordinary store. Non-evaluation ordinary seals explicitly use null for absent workload/role/registration/attempt/grant bindings; null never satisfies evaluation admission. Use the existing journal/transaction, not another database.

First evaluation binding permits an empty operational history plus the explicitly enumerated original-root/role allocation and bridge setup rows needed by OD1. It must reject any prior runs, inputs, checkpoints, development records, initiative state, tool observations, task artifacts or unaccounted requests. Inventory and initial workspace hashes are retained as fresh-state evidence; no imported learned state. Candidate and controls begin from equivalent independently prepared public task fixtures. The implementation freezes the exact allowed setup namespaces from the joined source before code; it may not use an open-ended prefix allowlist. Ordinary non-evaluation operation may keep existing state, but an unsealed used store cannot become an evaluation role.

Reopening requires the identical persisted seal, actual configuration and original bridge binding, with unchanged consumed grant and journal identity. Removing/changing the field, switching kinds, changing role, substituting Store, reseeding the workspace or deleting the seal is rejection, not automatic repair. An absent seal on a nonfresh evaluation store is rejection. A restart under the same mode retains work and uncertainty; it does not re-run freshness initialization. Root-qualified journal/host isolation establishes resistance to malicious host edits; a local row is not cryptographic proof against a compromised operator. Nothing here authorizes mode changes within an attempt or changing its candidate closure after registration.
