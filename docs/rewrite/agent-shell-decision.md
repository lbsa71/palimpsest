# Agent shell: reuse, fork or build

**Status:** decision procedure and researched shortlist, 2026-10-11. No shell has been selected, installed or benchmarked for the rewrite. A1-L02 owns the experiment; A1-L01 supplies contracts; A1-L08 supplies independent acceptance and comparison. [Architecture](architecture.md) defines the boundary. [ADR 0031](../adr/0031-aeon-rewrite-and-prompt-sovereignty.md) makes prompt ownership and the full rewrite accepted direction.

## Recommendation

Evaluate reusable shells first, with Pi and DeepAgentsJS as the initial broad candidates, AI SDK as the smaller composable option, and local Codex as a serious reuse/fork candidate. Include Claude Agent SDK in the control audit and as an execution baseline; its suitability as the primary mind remains conditional on effective instruction control and whole-system evolvability. This ordering is an engineering hypothesis, not a scored result.

The shell should supply good model/tool iteration, working-context management, streaming and session mechanics. Palimpsest should own its continuing identity, autobiographical state, goals, evidence, authority and effect accounting. Reimplementing a mature action loop is expensive; importing a second incompatible state machine or an unremovable assistant persona can be more expensive. Compare total integration and maintenance effort, not package size or brand familiarity.

Reject the old implicit equation of a thin provider adapter with an agent harness. A protocol adapter remains useful plumbing, but does not itself provide planning, tool use, observation, repair, delegation or long-task continuation.

## Effective instruction control is a hard gate

Primary-mind candidates must pass all of the following before their performance score matters:

1. **Replace and remove:** replace the base persona and selectively remove all library-authored behavioral fragments that conflict with the Autark's chosen identity and development. Append-only customization fails. A maintainable local fork can satisfy the requirement.
2. **Observe the application boundary:** account for all instructions in the final emitted requests, including tool descriptions, reminders, project discovery, skills, model profiles, retries, compaction, child agents and resumed sessions. SDK output events alone are insufficient.
3. **Retain functional capability:** the owned instruction set still supports effective tools, investigation, verification and continuation. Passing a string-removal test while crippling the loop is not a useful adoption result.
4. **Enforce execution boundaries:** all relevant model requests and external effects pass through the runtime's resource and authority contract. A library's verbal promise or an after-dispatch hook is insufficient.
5. **Own continuity:** durable self, goals and operation receipts remain readable and usable when the shell is replaced. Library checkpoint state has an explicit relationship to canonical state.
6. **Evolve the implementation:** source and license permit required local modifications, or the component is explicitly replaceable with an adequate alternative. A primary shell that permanently blocks changes to necessary cognition or orchestration is unacceptable.

These gates concern application-controlled machinery. They do not promise to remove learned model dispositions or inaccessible provider-side policy. If those materially interfere with the product, evaluate an alternate provider/model or a local model with measured capability and cost. Record the limitation rather than disguising it as a solved prompt problem.

A delegated specialist can be considered separately even when it fails the primary-mind gate. It receives a bounded task, scoped evidence and an output contract; it does not author the Autark's identity or control its agenda. Its output is attributed and evaluated. Such use still requires the relevant data, resource and effect permissions, and must show that the benefit exceeds the dependency cost. A failed primary-mind candidate is not automatically approved as a specialist.

## Finite bakeoff

This is A1-L02's proposed experiment envelope, not authorization for new paid calls or installs. The lane freezes its actual authorized time, cost and provider limits before execution. Caps are maximums, not targets, and no experiment may silently borrow an unrelated operating allocation.

| Stage | Concrete work | Bound and exit |
| --- | --- | --- |
| 0: freeze | A1-L01 supplies draft shell/runtime/prompt contracts; A1-L08 supplies a fixed case set, scoring procedure and resource accounting. Record candidate versions and allowed environments. | One coordination session; publish missing prerequisites instead of testing against moving targets. |
| 1: source and deterministic audit | Audit all five reusable candidates in parallel. Build tiny synthetic request-capture and effect-interception fixtures, including failure/retry/resume paths. | At most one bounded session per candidate. Drop a hard-gate failure with evidence; if a fork fixes it, estimate the patch and maintenance before proceeding. |
| 2: integration shortlist | Select at most two reusable candidates by hard-gate feasibility and estimated effort. Implement the same minimal bridge, prompt manifest, two tools, checkpoint and cancellation path. Maintain a small custom reference loop only as a control. | At most two implementation sessions per shortlisted candidate. Stop when the contract is demonstrated or the integration cap is reached; report an unfinished candidate as unfinished. |
| 3: common-model comparison | Use the same authorized model, owned instructions, tools, task inputs and resource envelope where technically supported. Run the frozen twelve-case screen below three times per eligible candidate. | Thirty-six runs per candidate maximum. All hidden retries/compaction count. Unsupported common-model operation is reported separately, not approximated with a different model. |
| 4: select | Publish scored screening evidence, integration diff, unresolved risks, fork burden and an ADR choosing adopt, fork or custom fallback. | One decision session. A tie goes to lower measured integration/maintenance cost among passing candidates; missing evidence cannot become a pass. This closes substrate selection and enables L02's production adapter; it does not establish product parity. |
| 5: product qualification after integration | A1-L08 compares the assembled system against pinned Codex and Claude Code configurations on its broader corpus. Report each system's actual model and resources. | Use A1-L08's explicitly frozen budget after L02–L07 are integrated. This separate end-to-end comparison gates L08/L09 acceptance, not the earlier shell selection; a failure can trigger a scoped reconsideration. |

The twelve screening cases are: repository orientation; locate and fix a failing test; implement a bounded feature; repair after a tool error; research a factual question with source checks; reconcile contradictory evidence; perform a reversible multi-tool operation; continue after process restart; preserve commitments through context compaction; delegate independent subtasks and integrate them; recover an uncertain effect without duplicate dispatch; and replace every application-side persona fragment across a resumed and delegated run. The last six include deterministic contract checks; subjective fluency alone does not score them.

After hard gates, proposed weights are **verified task success 35%, interruption/continuation correctness 20%, measured integration and maintenance burden 20%, resource efficiency 15%, observability and evaluation support 10%**. A1-L08 must define scoring anchors and record raw outcomes before execution. Failure of prompt ownership, effect control or continuity cannot be averaged away by good coding scores. The screen chooses an implementation substrate; it is too small to establish broad parity or superiority.

Outputs are reproducible experiment files, exact versions, request manifests, effect traces, task artifacts, failures, call/token/cost/time accounting, dependency/license inventory, adapter diff and a reasoned adoption ADR. Record integration effort and the custom code still required, including missing features removed with default prompts. Compare the best local custom control honestly rather than handicapping it.

## Adoption and ongoing reconsideration

**Adopt upstream** when it passes hard gates, matches the behavioral floor and reduces total implementation burden with supported extension points. **Fork** when a bounded, tested patch removes a concrete incompatibility and maintaining it is cheaper than replacing the useful machinery. **Build custom** when none meets the hard gates within the finite integration cap, or measured integration burden exceeds a credible custom implementation. Unbounded framework shopping is not a fourth outcome.

A fork records upstream commit, license notices, local patch rationale, reproducible build, behavioral fixtures and upstream-update procedure. Neither upstream acceptance nor vendor approval is a prerequisite to using a lawfully maintainable local fork. The Autark can later evolve or replace this shell through the same independent release process as other components.

Reconsider the decision when evaluations show persistent deficits, required capabilities cannot be integrated cleanly, a dependency changes its instruction behavior or terms, recurring fork cost exceeds its value, or a stronger candidate materially changes the tradeoff. Every consequential runtime proposal includes a short reuse-versus-build assessment. Do not rerun the full bakeoff for routine local edits without a changed assumption.
