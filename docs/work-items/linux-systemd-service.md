## Problem and expected behavior

The former launchd installation cannot run on Linux. The destination needs a continuously serving systemd unit with private state/configuration/logs, bounded restart and shutdown, and an exact native admitted host. Hourly plan allocations belong to the running scheduler; stopping and starting Slack each hour would lose responsiveness.

An operator prepares a private staging projection of the current native known-good source after the migration readiness gate passes. Root installs that projection under root-owned `/opt/palimpsest/hosts/<digest>` and its checksum list under root-owned `/etc/palimpsest`. An independent systemd `ExecStartPre` coreutils checksum check binds every source byte and the Node binary before importing any application startup code. The service executes that sealed projection, validates its complete frozen identity/runtime/toolchain, and compares its governance with current custody before starting. Compatible cognitive promotions retain the host; changed host governance requires a new operator preparation and unit digest. The existing coordinator lock prevents two destination owners of one store. The separate migration protocol establishes source-host shutdown and provider-free destination recovery before readiness; this unit cannot establish cross-host exclusion by itself.

## Acceptance and evidence

A generated unit or active PID alone is not those live checks.

## Non-goals, dependencies and risks

No live deployment/account changes, secret values in units, new provider calls, arbitrary executable paths, autonomous host admission, or generic service framework. The lead installs the actual unit and migration account/filesystem. Dependencies: native Node 24, independently reviewed Linux isolation, admitted migration/custody records, existing candidate verifier and coordinator lock, root-controlled systemd unit and independently installed checksum anchor. Root sealing is this operator migration route, not a claim that autonomous P18 host evolution exists. Linux runtime and platform-specific dependency identities must be native; old Darwin artifacts remain history, not runnable fallback.

Systemd grants network and user namespaces needed by the host and its Linux sandbox; it is not a replacement for tool isolation. Shutdown first signals only the main process to let the CLI cancel/drain, then kills the cgroup after a finite deadline. Abrupt kill leaves uncertain effects for existing recovery, never an assumed success. Shared runtime tools and unrelated processes must survive. File logs are private but retention/rotation remains an operational obligation. Root must smoke an actual sandboxed worker/check using service scratch; local rendering cannot prove Linux namespace behavior. Root must verify target systemd support for append logging and user-namespace restrictions. No live systemd behavior is claimed by local fixtures.
