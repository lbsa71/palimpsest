# P17 durable coordinator and receiver tools

Status: implementation work item, 2026-10-10. Governing requirements and acceptance are the approved [durable-session contract](p17-durable-coding-session.md), [coding specification](../coding-autonomy.md) and [ADR 0019](../adr/0019-coding-autonomy-and-reusable-agent-plumbing.md). This component does not establish serving acceptance by itself.

Problem: actual workspace receivers are inaccessible through a persistent model/tool conversation. Expected behavior: a host-admitted finite session imports verified source, records each intended request and entire validated response batch before effects, executes sequentially with stable identities, persists observed receipts, and continues from command failure to repair. Completed responses survive interruption without reinference, while possibly applied operations reconcile instead of replaying. A native single-step factory remains injected until retained production dependencies exist.

Acceptance: RED coordinator/receiver fixtures precede implementation; current origin and epoch checks gate admission, reservations, every effect and accepted asynchronous results; mixed invalid batches have zero effects; physical dispatch uses one ledger reservation after acquiring its provider slot; cumulative accounting/draft lineage survive reopen and budget waits; all model-facing file, staged-command/output, stable-diff and exact-submission operations use the actual receivers; pause drains owned operations, cancellation terminates execution, successor adoption preserves historical base, and terminal/report delivery remain separate. Root integration must separately exercise actual ingress, worker/native conversion and follow-up delivery.

Dependencies: existing Store, CodingWorkspaces, staged commands; independently owned CodingAccounting/state and CodingArtifacts import/submission. Owned implementation files are coding-provider/contracts/session/tools and their coordinator/tool tests. Non-goals: replacement ledger, current release admission changes, production dependency installation, live inference, network/spending, activation/publication, or hidden model patches. Material risks: SQLite and filesystem are distinct transactional resources; cancellation is not a refund or proof of remote outcome; missing/reused PID evidence must remain held; transcript shape is not trusted result provenance; synchronous trusted validation must be finite.

Implementation choices within the approved contract: an internal `coding-session` task owns workspace effects; an explicit configured policy admits finite limits with no new allocation defaults; SDK-free records and a single sequential coordinator bind all tools to that task/workspace/epoch; retained complete call-ID history survives bounded model transcript selection; submission records immutable evidence and a separate disposition. The coordinator exposes admission/status/tick/pause/resume/cancel/stop/adoption and current receiver authorization to the host.

## Public host contracts

`CodingSessionCoordinator` takes Store, CodingAccounting, CodingWorkspaces and CodingArtifacts, current epoch/origin/session authority callbacks, an explicit finite `CodingSessionPolicy`, a provider-slot receiver and an optional single-step `providerFactory(gates)`. The factory receives the persisted session, five trusted tool definitions, finite provider limits and synchronous `preauthorize`/`reserve` hooks. The host chooses model/key/transport outside model messages; production availability requires a retained dependency/factory route. SDK-free records live in `coding-provider.ts`; none of the coordinator's public interfaces import SDK types.

`admitTask(task, objective)` accepts only independently authorized direct/Slack origins. `admitGrowth(task, objective)` requires a distinct trusted `coding-origin` authorization. Concurrent matching admission shares one verified source import; a different objective conflicts. Admission resolves only after an immutable source artifact, exact file/directory/root-mode workspace import and final ledger contract exist. An already charged conversation or retained independent growth admission decision is linked once into session/work/attempt ceilings. Growth linking references the actual scheduler reservation journal sequence and does not debit its shared window twice. Manual host-origin admission with no provider decision creates no fictional call. The final contract seals policy, initial manifest/layout, source artifact, historical base, origin and report binding. Asynchronous authority answers and nonfinite policy values grant nothing.

`tick()` performs at most one model step or one pending tool operation; `runReady(maxTicks)` requires an explicit finite bound. A model step persists its intended request before waiting for a slot and spends only when the native physical transport calls `reserve`. The full validated response batch and raw argument strings become durable before tools. Each tool records a stable effect identity before execution and derives its model result from actual Store/receiver evidence. Completed receipts may be reused only for their matching task/workspace/intent. The host retains all native IDs even when selecting bounded complete groups for model context.

`pause()` aborts admission/model waits and drains owned receiver work without permanently stopping the receiver. A consumed request without an accepted response remains spent and unknown. `resume()` re-enables interrupted/reconciliation phases; budget wakeups keep their original timestamps. `adoptEpoch()` first retires expired or revoked execution so an old unavailable draft cannot veto worker recovery. It drains positively owned local work, retains unresolved effects/writer claims and records the terminal outcome without renewing that draft. Eligible drafts renew current authority only through actual quiescent receiver adoption, preserving historical base, policy, spent calls, receipts and draft; a genuine receiver adoption failure still requires reconciliation. `stop()` finally closes the receiver; a successor constructs a fresh coordinator/receiver. `cancel(id)` aborts and settles a matching pending admission before returning, records a durable cancellation so that late source or repeated admission cannot grant execution, and otherwise records a terminal cancelled owner while retaining the draft. Cancelled origin state independently revokes execution; normally completed foreground origins remain valid for their already admitted coding work. Uncertain effects require existing receiver reconciliation, never raw mutation/command replay.

Expiry maintenance visits every inactive/waiting session, including waits without wake times, aborts and drains owned active work, and terminalizes expired execution without another inference or raw-effect replay. Unresolved receipts remain held; ending execution does not supply missing reconciliation evidence.

The optional `authorizeOutcome(session, originTask)` is a separate reporting gate. By default, only the sealed originating scope may receive an outcome; the execution whitelist does not suppress the already owed return. Revoked execution authority receives a bounded host summary with no source/tool transcript. The optional `onOutcome({session, originTask, summary})` registers an owed host outcome independently of outbound delivery or release activation. Terminal execution alone does not show a delivered report or admitted release. Root serving integration owns those later transitions.

## Tools and result bounds

The catalog exposes `workspace_files` (manifest, paged list, literal search, full/ranged read, create/replace/exact edit/delete/move/mkdir/rmdir), `workspace_command` (staged Node/native TypeScript), `workspace_output` (sealed opaque call identity and byte coordinates), `workspace_diff` and `workspace_submit`. Model arguments cannot choose a task, epoch, host path, authorization, helper observe/checkpoint operation or admission disposition. A mixed invalid batch, duplicate ID or mixed submission batch creates no receiver effects.

Tool results sent to the model have a 16 KiB bound; complete original receipts remain durable. Oversized lists/searches preserve exact structured continuations, reads expose the next observed byte, and output pages retain exact base64 bytes and offsets. Search line previews explicitly mark omitted context. Diff pages retain before/after file identities, directory-name view identity, file modes and bounded text hunks; stale views/cursors fail. Directory addition/removal is visible. Directory/root mode evidence is preserved by exact import/submission; the existing listing receiver does not provide current directory modes for diff presentation. Binary text hunks remain explicitly unavailable, with complete bytes retained in submission. Broader pattern/regex discovery, additional commands/dependencies and general source release admission remain the limitations tracked by the governing P17/P18 specifications.
