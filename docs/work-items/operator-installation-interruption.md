# Operator installation interruption

Status: source repair implemented with focused and affected-file fixture checks; independent review and integrated acceptance remain open, P1, 2026-10-10. Source review of collector integration `f7f4415`, runtime reproduction against `ed1cf96`; no release acceptance. Applies to P12/P13, R17–R19 and [ADR 0024](../adr/0024-serving-responsive-candidate-collection.md).

## Problem and evidence

Before this repair, the CLI's stop handler aborted the signal supplied to Git publication, but `host-baseline install` did not pass that signal to `GenerationHost.installHostBaseline` or check stopping before installation. Stopping the runtime does not revoke the worker's custody authority. Host collection was aborted only when `host.close()` ran in `finally`, after the awaited installation returned. Source review found a reachable path where SIGTERM during verification could be followed by custody preparation, fencing and activation before cleanup.

The earlier full source run separately timed out the original operator installation command at its unchanged 20-second deadline; it produced empty successful output after SIGTERM. That observation does not by itself prove post-stop activation. An unchanged isolated rerun and the integrated source run's operator case pass. Neither exercises this interruption boundary. The actual CLI reproduction below now demonstrates post-stop custody mutation; the earlier source finding alone was not a runtime reproduction.

Relevant receivers are [the CLI](../../src/cli.ts), [GenerationHost](../../src/generations.ts) and [Custodian](../../src/custodian.ts). The evaluator and custodian bytes remain unchanged by the collector correction.

## Expected behavior and acceptance

- Before transfer is committed, stopping prevents new collection stages and installation admission. Cancel positively owned work and retain ownership until actual drain; unknown cleanup remains held.
- Revalidate interruption at the queued custody boundary and after verification, alongside the existing incumbent and authority checks. A completed verifier is evidence, not permission to continue a stopped operation.
- After transfer has crossed its irreversible boundary, finish the necessary mechanical reconciliation or retained recovery. Do not abandon a fenced successor, rewind current memory, refund spent calls or replay an uncertain effect.
- Reproduce the pre-transfer race with the actual operator CLI and blocked collector, then show no new preparation/fencing/activation after the stop. Exercise interruption around transfer separately and verify recovery, current memory and exact release identity.
- Retain the original operator deadlines, assertions, protected checks, evaluator identity, grants, budgets and configuration. Report an interrupted command honestly rather than treating empty output as successful installation.

## Scope and completion

The operation signal applies before host collection launch, at queued custody admission, and after every pre-fence asynchronous artifact verifier. The final cancellable boundary is the verifier immediately preceding `host_baseline.fenced`. Once that event increments the epoch and clears the active owner, the same operation must finish installation or bounded recovery despite a stopped caller. Recovery uses current state and the retained known-good artifact, without inheriting the stopped admission signal. A CLI stop reports a nonzero interrupted outcome with the resulting phase and exact release identities, including an installation that mechanically completed after fencing. This implements the existing ADR 0016/0024 contract without changing Custodian admission or recovery rules. Dependencies are the existing custody queue, collector ownership/drain and original operator fixture.

Non-goals are Git discovery optimization, broader release authority, retained-environment implementation and general coding integration. The material risk is cancelling at the wrong phase and leaving custody fenced or cleanup unproven.

Done when actual failing behavior is reproduced, the phase-specific repair and recovery checks pass, independent review resolves the finding, and the installation contract and evidence agree. The source merge does not close this item or authorize deployment of the collector correction.


## Repair and recorded fixture evidence

`GenerationHost.installHostBaseline(manifest, expectedIncumbent, signal?)` now rejects an already stopped operation, supplies the operation signal to each host preflight collector, and checks it in the queued current-incumbent validator. The custody context retains its entry epoch and operation signal. Only private pre-fence artifact verification inherits that signal; the final asynchronous result is checked again before its consequence is consumed. A fenced epoch or the explicitly mechanical recovery verifier does not inherit a stopped admission signal. Collector cancellation still uses the existing positively owned helper/checker cancellation and drain contract; an unknown receipt stays held and blocks later collection.

The CLI passes its existing stop signal to installation. A requested stop produces exit code 1 and a JSON `status: interrupted` receipt with observed phase, active generation, known-good identity and reason. If fencing already occurred, the receipt follows mechanical completion or recovery and describes that resulting state. Ordinary successful output retains its existing shape. This pre-fence cancellation contract applies to new `install` admission. `restore` remains the existing bound mechanical rescue through Custodian, without an installation admission signal; a stopped CLI reports its resulting restoration state honestly after that rescue settles. No evaluator, Custodian, collector backend, grants, dependencies, configuration or operator command deadline changed.
